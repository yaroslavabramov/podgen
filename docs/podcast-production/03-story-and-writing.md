# 03. История и сценарий

Спецификация целевой реализации, 4 ноября 2026. Общие типы — [00](00-system-contract.md), исследование — [02](02-research-and-editor.md), независимая оценка — [04](04-verification-and-evaluation.md), исполнение — [05](05-audio-production.md), runtime — [06](06-platform-and-runtime.md).

Редакция от 5 ноября 2026. Как выбирать историю, писать для слуха, различать голоса и править переходы, показано на одном материале в [практике автора и редактора](03-editorial-practice.md).

## 1. Ответственность и результат

Модуль превращает досье в историю, которую можно понять на слух: вопрос, развитие объяснения и ответ с честными ограничениями. Он отвечает за замысел, композицию, реплики, переходы, связность, память о рассказанном и редактуру всего сценария. Истинность окончательных утверждений независимо проверяет 04; естественность исполнения и соответствие речи тексту — 05.

План — рабочее предположение о том, как рассказать материал. Автор может обнаружить лучший порядок или слабость самого объяснения. Изменение плана разрешено; незаметная смена исходного вопроса пользователя — нет. Новый факт в каждом блоке не требуется: переход, пауза, пример и возвращение к знакомому могут менять понимание без нового claim.

Выпуск не должен превращаться в озвученный реестр источников. Подробные ссылки доступны через transcript/show notes. В речь входят атрибуции, важные для смысла: кто утверждает, насколько это установлено, к какому времени относится и где остаётся спор. Technical IDs и Markdown citations не произносятся.

## 2. StoryPlan

Основные результаты — ArtifactRevision. Ниже payload; backend назначает IDs, producer и зависимости. StoryOption, ActPlan и локальные селекторы — вложенные значения, не отдельные задания модели.

```text
StoryPlan.payload = {
  episode_spec_ref, dossier_ref, editorial_decision_ref,
  main_question, listener_promise, working_answer,
  selected_option_id, considered_options: StoryOption[],
  opening: {approach, material_refs[], question_to_open},
  acts: ActPlan[],
  ending: {answer_to_deliver, qualifications[], promises_to_close[]},
  host_functions: [{speaker_id, contribution, interaction_guidance, speech_register}],
  duration_strategy: {estimated_seconds_range, assumptions, optional_material[]},
  unresolved_research_request_refs: ArtifactRef[]
}
StoryOption = {
  option_id, angle, route_summary, strongest_material_refs[],
  listener_benefit, weakness, research_needed[], selection_reason|null
}
ActPlan = {
  plan_act_id, title, listener_question, intended_change_in_understanding,
  prerequisite_concepts[], material_refs[], limitations_to_voice[],
  transitions: {from_previous, toward_next},
  promises_opened[], promises_addressed[],
  estimated_seconds_range, priority: essential|optional
}
```

Working answer допускает объяснение обоснованной неизвестности. Два варианта не являются условием сохранения: один очевидный способ объяснения допустим. При нескольких содержательно разных вариантах редактор сравнивает, что слушатель поймёт, какие материалы есть и где пришлось бы выдумывать связку. Количество сцен/фактов не определяет победителя.

ActPlan описывает изменение понимания, а не атомы для обязательного расходования. Material refs ведут к полным ResearchNote/EvidenceSpan/CalculationRecord; preview не заменяет механизм и оговорки. Порядок может быть тематическим, причинным или хронологическим: он помогает понять вопрос, а не повторяет порядок найденных источников.

Начало открывает вопрос или значимое противоречие, доступное материалам. Документальную сцену нельзя дополнять выдуманными действиями, мыслями или цитатами. Условная иллюстрация явно названа условной. План не задаёт все реплики заранее и не требует одинакового размера актов.

Host functions заданы в рамках EpisodeSpec. Один ведущий может вести весь рассказ. Несколько ведущих получают полезные функции: предъявить наблюдение, проверить понятность, развить объяснение, поставить контрпример. Не нужны постоянный «незнайка», искусственная ссора, регулярное восхищение и смена голоса после каждого предложения.

Планировщик передаёт автору связный `route_summary` выбранного варианта. В нём есть начальное представление слушателя, материал, который его меняет, и ответ, которым закончится история. `speech_register` описывает манеру речи на языке выпуска с учётом пожеланий пользователя. `contribution` объясняет, какую работу ведущий выполняет именно в этой истории. Для трудного места `ActPlan.intended_change_in_understanding` называет различие или причинный шаг, который слушатель сможет объяснить своими словами. В материалах акта должна открываться опора для этого шага. Отсутствующее основание становится вопросом исследователю.

## 3. Сценарий, идентичность и адресация

```text
ScriptRevision.payload = {
  episode_spec_ref,
  story_plan_ref: ArtifactRef|null, dossier_ref: ArtifactRef|null,
  parent_script_ref: ArtifactRef|null,
  mode: exploratory|production,
  completion: fragment|draft|complete,
  acts: ScriptAct[],
  author_support_bindings: SupportBinding[],
  plan_departures: [{description, rationale, affected_plan_act_ids[]}],
  open_research_request_refs: ArtifactRef[]
}
ScriptAct = {act_id, plan_act_id|null, title, draft_tail: open|closed, blocks: ScriptBlock[]}
ScriptBlock = {block_id, function_note|null, items: ScriptItem[]}
ScriptItem =
  {kind: utterance, utterance_id, speaker_id, text}
  | {kind: stage_direction, direction_id, purpose, text}
  | {kind: research_placeholder, placeholder_id, question, request_ref|null}
LocalScriptSelector = {
  act_id, block_id, item_id,
  char_start: integer|null, char_end: integer|null
}
ScriptSelector = {script_ref: ArtifactRef, selector: LocalScriptSelector}
SupportBinding = {
  selector: LocalScriptSelector, basis_refs: ArtifactRef[],
  relation: direct|interpretation|illustration, note: string|null
}
```

Item ID разрешается в utterance_id, direction_id либо placeholder_id. UUID создаёт backend; модель использует aliases существующих элементов и локальные метки новых. Char offsets — Unicode code points в сохранённом text, полуинтервал `[start,end)`. Backend вычисляет диапазон по показанной выборке/цитате; автор не считает позиции вручную. Null offsets означают целый элемент; несколько элементов адресуются несколькими selectors. Индексы не относятся к HTML или склеенному Markdown.

В utterance.text находятся только произносимые слова и пунктуация. Citations, исследовательские вопросы и ремарки — отдельные поля/элементы. Stage direction описывает намерение исполнения, но не разрешает менять смысл реплики. Директива из цитируемого источника остаётся данными.

`spoken_view(script_ref)` строится кодом и возвращает `{script_ref, algorithm_version, view_hash, utterances:[{selector, speaker_id, text}]}`. В `utterances` попадают только произносимые реплики, в порядке воспроизведения. `selector` занимает ровно текст реплики в данной версии. Заголовки актов, `function_note`, ремарки, placeholders и авторские ссылки доступны в полном ScriptRevision. Одинаковые реплики в разных местах остаются разными элементами. `view_hash` вычисляется по версии алгоритма и упорядоченным локальным селекторам, speaker IDs и дословному тексту по правилам 06. Сам `script_ref` всегда закреплён отдельно. Представление используется для анализа рассказанного, первичного извлечения claims и первого чтения редактором. Для аудио 05 дополнительно получает ремарки отдельным каналом.

`completion=complete` требует произносимого текста, закрытых `draft_tail` и отсутствия `research_placeholder`. В завершённом production-диалоге должны действительно звучать заявленные ведущие. Полезность их участия проверяет редактор по самим обменам. В production draft открытые хвосты и placeholders допустимы. Вход 05 требует production + complete, действующих допусков 04 и пустой проекции действующих блокирующих запросов для этой ветки и версии.

Для exploratory fragment до первого плана story_plan_ref может быть null; до интеграции первых материалов dossier_ref также может быть null. Тогда полученный текст явно исследовательский, непроверенные положения — placeholders, а известные входы закреплены в manifest. Production требует оба refs. StoryPlan.editorial_decision_ref указывает предшествующее поручение/решение о направлении, а не будущий акт принятия этого же плана: иначе возникнет цикл.

Act/block/utterance IDs сохраняются, пока сохраняется логическая единица. Перемещение сохраняет ID; изменение текста создаёт новую ScriptRevision с тем же ID. При разделении/слиянии назначаются новые IDs и lineage mapping. Удалённый ID не переиспользуется. Два одинаковых предложения в разных местах — разные utterance IDs. Изменённый текст не наследует прежние offsets или approvals.

ScriptAct не обязан один к одному повторять ActPlan. Автор вправе перестроить draft и описать plan_departures; редактор принимает обновлённый план либо обоснованное отклонение после просмотра полного текста. Не вводится schema gate, заставляющий подгонять хорошую сцену под старый план. Финальная EditorialReview оценивает конкретную пару plan/script и исходное обещание.

Author support bindings помогают навигации и не являются готовым ClaimSet. Автор может ошибиться или пропустить утверждение. 04 извлекает claims из фактического текста, проверяет полноту извлечения и читает первоисточники независимо от самооценки автора. ResearchNote — контекст объяснения, а не замена evidence.

### Изменения и dependency DAG

```text
ScriptChangeSet.payload = {
  base_script_ref, next_script_ref, change_reason,
  operations: [{kind, before_selectors[], after_selectors[], rationale}],
  identity_map: [{old_item_ids[], new_item_ids[], relation: retained|split|merged|removed|inserted}],
  research_request_dispositions: [{request_ref, action: still_open|addressed|obsolete,
                                 new_selectors[], rationale}],
  dependency_dispositions: AuthorDependencyProposal[],
  declared_impact: {structure, spoken_text, evidence_basis, speaker_assignment}
}
```

Первый `create` сохраняет ScriptRevision с `parent_script_ref=null` и возвращает `change_set_ref=null`. Для каждой следующей правки backend сохраняет новую версию и ScriptChangeSet с обязательными `base_script_ref` и `next_script_ref` в одной транзакции. Повтор той же операции возвращает тот же результат. Parent и base сохраняют происхождение. Действующие зависимости текста и порядка определяются для новой версии по правилам 06.

AuthorDependencyProposal — локальное предложение автора: `{input_ref, proposed_action: retained|replaced|removed, replacement_refs[], affected_selectors[], rationale}`. Если неверный факт удалён либо получил новую опору, предложение описывает изменение, но не снимает invalidation. После проверки 04 оно нормализуется в канонический DependencyDisposition из 00; локальные поля не создают второй runtime-контракт. Проверяющий подтверждает достаточность текущей опоры и отсутствие прежнего вывода/материала; runtime связывает оценку с exact revision. Пока предложение не проверено, действует консервативная invalidation policy. Полный trace входов остаётся: история получения текста не тождественна текущей доказательной зависимости. Declared impact тоже проверяется фактическим diff, а не заявлением «только косметика».

ResearchRequest указывает на сохранённый Script@N. Следующая Script@N+1 может ссылаться на request; Script@N не дописывает ссылку задним числом. При правке места request остаётся привязанным к N; ChangeSet отображает его на новые selectors или объясняет obsolete. Совпадение номера акта не переносит запрос автоматически.

## 4. ListenerState по написанному тексту

```text
ListenerState.payload = {
  script_ref,
  covered_prefix: {through_item_id: UUID|null, ordered_item_ids[], content_and_order_hash},
  audience_assumptions: [{assumption, basis: episode_spec}],
  introduced_entities: [{entity, aliases[], introduction_selectors[]}],
  explained_concepts: [{concept, explanation_summary, supporting_selectors[], depth}],
  established_connections: [{connection, supporting_selectors[], qualification}],
  questions_and_promises: [{statement, opened_at[], status: open|partly_answered|answered|explicitly_unknown,
                          addressed_at[], rationale}],
  comprehension_risks: [{description, selectors[], proposed_action}],
  extractor_profile_ref
}
```

Это оценка того, что предъявлено слушателю, а не доказательство понимания. Состояние извлекается из фактического prefix, включая порядок/формулировки. План не может заранее «закрыть» обещание. Mention понятия не считается объяснением механизма; source ID не считается введённой сущностью. Проверка 04 и слушательские эксперименты оценивают полезность представления.

После сохранения акта отдельный анализатор получает новый текст и весь релевантный предыдущий prefix. Он связывает состояния с конкретными репликами. Прежний ListenerState можно использовать как память; спорные закрытия/повторы проверяются по полному script через read tools. Нельзя бесконечно строить summary от summary, теряя исходный смысл.

Prefix здесь и далее означает непрерывное начало `spoken_view`. `ordered_item_ids` содержит только IDs произносимых реплик. `content_and_order_hash` использует тот же алгоритм, что `view_hash`, применительно к покрытому началу. Для итогового EditorialReview нужны `script_ref` точной версии и hash всей `spoken_view`. Позиция на последней реплике последнего акта сама по себе ещё не подтверждает покрытие середины. Анализатор отмечает объяснение только по доступным слушателю словам. Имеющиеся у аудитории знания берёт из EpisodeSpec. Если ответ удаётся восстановить по собственному знанию или по ремарке, место в тексте остаётся открытым.

Начальная точка — пустой prefix: through_item_id=null, ordered_item_ids=[], hash пустой canonical последовательности; остаются только явно заданные предположения об аудитории. При reorder/удалении/смысловой правке backend находит первую изменённую позицию; состояния затронутого suffix устаревают. Prefix hash учитывает IDs, текст, speaker и порядок. Если точность dependency map не доказана, пересчитывается всё состояние. Совпадение последнего act ID не разрешает reuse.

Writer получает и ListenerState, и реальный предыдущий текст. Противоречие между ними разрешается чтением текста и новой revision состояния. Ledger не запрещает полезный callback: оцениваются новая функция возврата и польза слушателю, а не повтор слова.

## 5. Алгоритм планирования и письма

1. **Поставить историю.** Получить полный EpisodeSpec, EditorialState и релевантное досье. Выбрать способ объяснения с редактором. При отсутствии центрального понимания создать exploratory fragment и точный ResearchRequest; не замещать пробел убедительным тоном.
2. **Сохранить StoryPlan.** Обещание, движение понимания, опоры, финал, оговорки и роли ведущих. Оценить длительность. Alternatives нужны там, где меняют результат.
3. **Выбрать способ письма.** Исходный вариант — писать непосредственно для выбранных ведущих. В EXP-04 испытывается и другой путь. Один из объявленных ведущих проговаривает связное объяснение в `exploratory` ScriptRevision. Автор получает этот текст вместе с досье и превращает его в разговор. Проверяет сохранение причинных связей, оговорок и атрибуций и отдаёт второму ведущему самостоятельный вклад. Пробный рассказ сохраняется целиком. Независимо выбирается размер единицы записи — весь выпуск, акт или продолжение открытого акта по протоколу ниже.
4. **Написать связный кусок.** В режиме acts автор получает глобальный план, полные релевантные notes, ранее написанный текст, конец предыдущего акта и ListenerState. Он пишет акт целиком, включая переходы, а не независимые биты без истории.
5. **Сохранить и обновить понимание.** Structural validation → ScriptRevision/checkpoint → ListenerState по реальному prefix. Локальный review обнаруживает недостающий переход, но не подменяет итоговую оценку выпуска.
6. **Доисследовать адресно.** Ответ 02 содержит полные notes, evidence, ограничения и новый dossier ref. Автор явно меняет текст; приход note сам реплики не переписывает.
7. **Отредактировать целиком.** Порядок, повторное объяснение, темп, соотношение вопроса/ответа, незакрытые promises, осмысленность диалога и честность финала. Разрешены перенос/удаление актов и новое начало, а не только мелкие patches.
8. **Передать точную версию 04.** Фактчек и EditorialReview по полному production script. После правок повторно проверяются затронутое и целостность. Принятый комплект поступает 05.

Последовательные акты — исходная организация для зависимого рассказа, не доказанно лучший универсальный алгоритм. Параллельно можно пробовать варианты начала или исследовать материалы. Два автора не добавляют соседние акты в общую ветку без фактического prefix. Их результаты — proposals; редактор интегрирует их последовательно и проверяет переходы.

## 6. Контекст и инструменты

Ниже описан целевой интерактивный режим. Текущая whole-episode оценка использует [смысловые входы по ролям](08-editorial-inputs.md): исходники целиком сохраняются на сервере, автор получает принятые решения и выбранные карточки, а ревьюер — необходимые атрибутированные выдержки. Эти вызовы не имеют read/research tools; наличие полного оригинала в хранилище не означает доступ к нему из модели.

| Обязательная часть | Что получает модель |
|---|---|
| Назначение | Цель конкретной работы, EpisodeSpec, язык/формат и вопрос слушателя |
| Вся история | Полный StoryPlan, предполагаемый ответ, значимые alternatives/uncertainties |
| Понимание темы | Полные релевантные ResearchNote, механизмы, ограничения; открываемые оригиналы |
| Написанное | Весь script, когда помещается; иначе полный текущий акт, предыдущий акт/переход и доступ ко всему остальному |
| Память | ListenerState с exact coverage, открытые promises, адресные риски |
| Действие | Полный feedback текущей правки, инструменты, способ сохранить partial |

Полнота сохранённого оригинала обязательна. Представление для роли выбирается по её задаче: вместимость окна сама по себе не оправдывает передачу всего корпуса. В целевом интерактивном режиме полный релевантный текст используется там, где он нужен для действия, и когда помещается вместе с полезным output. Уменьшение контекста явно: отдельные DerivedPreview с refs/coverage и read_script для полного текста. Резервируется output capacity выбранной единицы письма; постоянные «25% окна» не гарантируют вместимость длинного сценария. Если обязательные данные не помещаются, `context_capacity_exceeded` требует другого профиля/единицы работы/адресного синтеза, а не усечения полей.

Если при продолжении длинного акта уже написанный акт сам превышает окно, compiler передаёт точный текст стыка, цель всего акта, релевантные полные заметки и карту предыдущих блоков с доступом к каждому полному фрагменту. Автор открывает, в частности, первое объяснение повторно используемого понятия или обещание, которое собирается закрыть. `ContextAssembly` фиксирует показанные диапазоны и причины отбора. При недоступности необходимого фрагмента задача возвращает явную ошибку вместимости.

Для смысловой правки обязательны исходный фрагмент, замечание, соседний текст и глобальный замысел. Вызов «убери повторы» без прежнего сценария — дефект постановки, не причина добавлять gate. ContextAssembly и ReadReceipt 06 сохраняют, что было передано фактически.

| Tool | Model-facing аргументы | Результат |
|---|---|---|
| `read_story_context` | section: spec/plan/editorial/listener, alias? | Полный artifact, exact ref/coverage, continuation |
| `read_script` | script_alias, locator?: act/block/item/quote, context, cursor? | Точный текст/соседи, aliases/selectors; полный script доступен последовательным чтением |
| `read_dossier` | note/question alias, detail=full | Контракт 02: связное объяснение и evidence refs |
| `save_story_plan` | тело плана, base_plan_alias? | Новая plan revision; proposal редактору |
| `save_script` | base_script_alias?, operation, content, reason? | Полный script checkpoint. Для `create` change_set_ref=null, для правки возвращается соответствующий ScriptChangeSet |
| `request_research` | requester_alias, location?, question, why, current_understanding, acceptance_questions, impact, blocking, requested_outcome | ResearchRequest 02 и handoff |
| `finish_writing` | status, output_aliases, remaining_questions, next_action | TaskResult 00; answered не равен release-ready |

Source read tools 01 доступны по роли. Операции `save_script` включают `create`, `replace_act`, `insert_act`, `remove_act`, `reorder_acts`, `replace_items`, `replace_episode`, `append_blocks`. Backend назначает IDs и сохраняет полный текст. При запросе исследования из StoryPlan `location` может указывать на весь план или на `{plan_ref, plan_act_id}`. Для ScriptRevision действует ScriptSelector.

**Когда акт длиннее одного ответа.** До вызова runtime резервирует место для произносимого текста и структуры tool call. Автор сохраняет законченную группу реплик с `draft_tail=open`. Продолжение передаёт `base_script_alias`, существующий `act_alias`, `after_block_alias` для последнего блока (null для пустого акта), новые целые блоки и `close_act`. Backend сверяет base revision и хвост, атомарно сохраняет очередную версию с полным префиксом, ChangeSet и checkpoint. При повторном вызове с тем же ключом возвращает прежнюю запись. При изменившемся хвосте возвращает `stale_revision`. Автор перечитывает действующий план, префикс и стык. Преждевременно оборванный ответ остаётся диагностикой. `complete` требует закрытых хвостов всех актов. О закрытии говорит автор по содержанию акта. Операционные окна записи не диктуют границы сцен или размер реплик.

В request_research writer передаёт requester_alias сохранённого ScriptRevision или StoryPlan. Другие роли могут использовать виды requester из 02; backend проверяет допустимые kinds по роли. Location типизирован владельцем requester: для сценария это LocalScriptSelector, для плана — его стабильный элемент/поле; неопределённая строковая позиция не принимается.

Base script alias закрепляет ожидаемую revision. Сохранение proposal не означает принятие в editorial head; commit использует CAS/epoch 06. При stale base — `stale_revision` с открываемым diff; автоматического merge прозы по совпадению строк нет. ToolResult/Error — общий union 06. Предметные ошибки: `invalid_selector`, `duplicate_item_id`, `unknown_speaker`, `incomplete_output`, `validation_error`; ответ указывает поле и исправление.

Частичный provider stream сохраняется диагностически. Незавершённая реплика/JSON не выдаётся за ScriptRevision. Явно законченный полезный fragment/draft сохраняется с соответствующим completion и TaskResult.partial. Retry не присоединяет один акт дважды; идемпотентность 06 обязательна.

## 7. Prompt contracts и примеры поведения

```text
WRITER
Роль: автор цельного подкаста для {audience} на {language}.
Текущая работа: {objective}; ожидаемое изменение понимания: {purpose}.
Обещание и весь план: {story_plan}. Подтверждённое понимание: {full_notes}.
Фактически написано: {actual_script}; память/coverage: {listener_state}.
Продолжи вопрос, оставленный предыдущими произносимыми репликами.
В трудном месте покажи, кто действует, что меняется и почему.
При смене масштаба объясни, что связывает частный пример с общим выводом.
В диалоге дай собеседнику материал, из которого действительно следует его ответ.
Назови источник или оговорку в том месте, где они меняют смысл услышанного.
Различай документальную деталь, условный пример и слова ведущего о себе.
При отсутствии основания сохрани draft и задай адресный research request.
Сохрани завершённый кусок через save_script; затем finish_writing.
```

```text
SCRIPT EDITOR
Вход: полный сценарий, исходное обещание, досье и feedback.
Оцени, ведёт ли порядок к пониманию ответа, где потерян переход,
повторяется объяснение или финал открывает вместо закрытия.
Перечитай произносимый текст на каждом изменённом стыке.
Назови место сбоя и достоинства исходного отрывка, которые нужно сохранить.
Измени масштаб, необходимый для исправления, включая порядок актов.
Сохрани ограничения фактов. Назови основание существенных изменений
и изменённые места; не объявляй собственную правку принятой.
```

```text
LISTENER STATE EXTRACTOR
Вход: непрерывный префикс spoken_view с exact selectors и audience assumptions.
Извлеки введённое, объяснённое, связи, открытые/закрытые вопросы.
Для каждого содержательного состояния приведи поддерживающие реплики.
Не считай план доказательством предъявленного объяснения.
Если понятие только названо, не помечай механизм объяснённым.
Верни состояние и адресные риски, без скрытого внутреннего рассуждения.
```

Шаблоны версионируются и проверяются на ModelProfile. От модели нужны наблюдаемые основания правок, а не скрытый chain-of-thought. Feedback не складывается бесконечным списком старых указаний: текущая задача и действующие замечания компилируются с точными версиями, история остаётся в trace.

**Полезный возврат.** В акте1 уже объяснён механизм. Акт2 возвращает знакомый пример, чтобы показать ограничение. Это допустимо без нового claim ID. Плохой вариант заново даёт то же определение, затем повторяет итог акта1. Различие проверяется по функции фрагмента и пониманию слушателя, не string similarity.

**Недостающая причина.** Источник говорит, что пилот длился 12 недель. Хороший draft отделяет срок от неизвестной причины окончательного решения и создаёт ResearchRequest. Плохой вариант: «Из-за двенадцатинедельного пилота решение приняли» с той же ссылкой. Цитата числа не обосновывает причинность.

**Два ведущих.** Один показывает наблюдение, другой проверяет вывод контрпримером, первый уточняет границу. Это содержательный обмен. Плохой вариант: второму ведущему каждые две реплики приписывают непонимание уже объяснённого или восторженное согласие; роли не развивают рассказ.

## 8. Возврат из исследования и редакторские циклы

ResearchRequest создаётся по контракту 02. Blocking=none позволяет продолжать; passage оставляет конкретное место незавершённым; central_answer запрещает финализацию основной линии, но допускает exploratory письмо. Независимые места можно писать. Placeholder всегда виден в draft и никогда не скрывается ради apparent completeness.

Editor 02 интегрирует note/result и передаёт новый dossier/state ref. Новый writer TaskSpec содержит исходный request, полный ответ, ограничения, изменённые evidence и текущий script. Автор сначала проверяет, актуален ли запрос на новой версии текста, затем сохраняет правку. Дополнительная note может потребовать изменения всего угла истории; её нельзя просто вставить в случайный абзац.

При переходе с досье D1 на D2 редактор проверяет основание выбранной истории. Локальное уточнение позволяет сохранить композицию в новой версии плана P2. Если материал меняет центральный ответ, редактор пересматривает вступление, зависимые акты и финал. В обоих случаях P2 указывает на D2. Финальный сценарий ссылается на принятые P2 и D2 с той же EpisodeSpec. Во время черновой работы старый план остаётся доступным по исходной ссылке. Пригодность P2 подтверждает редактор через EditorialDecision и IntegrationEvent.

`open_research_request_refs` и placeholders помогают автору ориентироваться. Текстовый допуск, запуск синтеза и выпуск проверяют действующие блокирующие запросы по проекции регистрации и принятых решений редактора из 02/06. Редактор может закрыть запрос подтверждённым ответом или удостовериться, что зависимое утверждение удалено из всего нового текста, в том числе в пересказе. Удаление placeholder из draft само по себе ничего не закрывает. Для исправления замечания редактор сравнивает кандидат со стабильной исходной версией на тех же входах. Если полная перепись испортила удачный финал, допускается вернуться к нему и внести только нужную подтверждённую правку. Точная версия проходит оба вида проверки 04.

Цикл после полного текста: Script@N → независимые VerificationReport/EditorialReview → редакторское решение → Script@N+1 → новый ClaimSet/VerificationReport и whole-script EditorialReview. Положительный фактчек не закрывает отрицательную оценку истории. Отрицательный review без готовой инструкции переписывания всё равно требует редакционного решения, а не пропуска замечания.

04 может переиспользовать проверку неизменного утверждения как evidence нового review при доказанной идентичности смысла/контекста/источников. Старый report/AcceptanceRecord никогда не переносится на новую revision автоматически. Даже перестановка актов может изменить подразумеваемую причинность, место оговорки и полезность финала.

Начальная политика — до трёх последовательных глобальных revision rounds без нового содержательного направления. После повторного одинакового провала diagnostic task проверяет prompt, model-facing payload, доступность полного текста и tool trace. Editor меняет подход/постановку/qualified profile либо возвращает needs_attention с конкретной причиной. Это предел бесцельного цикла для калибровки, не разрешение принять дефектный выпуск после третьей попытки.

## 9. Длительность и передача в аудио

EpisodeSpec.duration — единственный источник target_seconds, tolerance_seconds и mode=target|strict. StoryPlan содержит оценку, а AudioMaster — измеренную длительность. Сценарий не получает готовность только из количества слов.

Оценка строится по языку, выбранным voice/format profiles, числам/аббревиатурам, паузам, диалогу и калиброванной скорости реального исполнения. Для неподтверждённого voice profile не используется уверенная универсальная норма words/minute. Перед полным синтезом 05 может проверить характерные блоки; результат помогает корректировать оценку, но не заменяет измерение финального master.

Если текст длиннее цели, редактор сокращает второстепенное, повторное объяснение и избыточные формулировки, сохраняя причинную цепь и оговорки. Если существенно короче — добавляет полезную глубину/пример/контрпример с исследованием при необходимости. Нельзя растягивать приветствия, дублировать выводы или ускорять голос до неестественности ради числа минут. При неразрешимом конфликте strict длительности и содержания пользователь получает needs_attention с вариантами изменить длительность/scope по правилам 06.

В 05 передаются точные script/plan/spec refs, approvals 04, ordered utterances, stable speaker IDs и nonspoken directions. PerformancePlan хранит нормализацию произношения и mapping к ScriptSelector. Неоднозначная замена имени, числа, отрицания или формулировки возвращается в 03; новая реплика проходит 04. Audio не становится вторым автором фактов.

После измерения master редактор получает фактическую длительность и адресные дефекты. Семантическое сокращение/расширение — новый ScriptRevision и повтор 04. Если достаточно поправить паузы/произношение в границах 05, script остаётся прежним, но новый master/alignment/AudioQA проверяются. Reuse сегментов разрешён только по ключам 05; изменившийся соседний контекст может требовать нового исполнения.

## 10. Сквозной пример

Учебный вымышленный корпус, продолжение примера 01. В протоколе есть «Тест длился 12 недель», причин окончательного изменения расписания нет. Writer сохраняет Script@5 с production/draft, двумя репликами и nonspoken placeholder. Диагностические aliases ниже заменяют реальные UUID; в persistence используются полные ArtifactRef.

```json
{
  "act_id": "a2",
  "plan_act_id": "pa2",
  "title": "Что показал пилот",
  "draft_tail": "open",
  "blocks": [{
    "block_id": "b4",
    "function_note": "Отделить известный срок от причины решения",
    "items": [
      {"kind": "utterance", "utterance_id": "u12", "speaker_id": "host_a",
       "text": "По протоколу, испытание длилось двенадцать недель."},
      {"kind": "utterance", "utterance_id": "u13", "speaker_id": "host_b",
       "text": "Но срок сам по себе не объясняет, почему изменили расписание."},
      {"kind": "research_placeholder", "placeholder_id": "p2",
       "question": "Каким основанием комиссия объяснила изменение?", "request_ref": null}
    ]
  }]
}
```

1. Sidecar binding u12 указывает на ev12 из 01. Фраза u13 рассматривается 04 как рассуждение, а не автоматически exempt.
2. Request R1 с requester_ref=Script@5, selector p2, impact=central_answer, blocking=central_answer сохраняется отдельно. Script@5 не мутирует.
3. Исследование получает решение комиссии; новый Dossier@9 содержит полный ответ и ограничения. Это условное продолжение fixture, не заявление о реальном учреждении.
4. Writer читает ответ и actual prefix, создаёт Script@6: заменяет p2 завершённым объяснением, при необходимости перестраивает акт. ChangeSet связывает p2 с новыми IDs, request отмечен addressed; редактор проверяет, действительно ли решён вопрос.
5. ListenerState@6 извлекается из нового текста. ClaimSet/VerificationReport/EditorialReview проверяют Script@6, а не @5.
6. Только production/complete без placeholders и с действующими approvals передаётся 05. При последующей правке u12 old audio/report не выдается за проверенную новую версию.

## 11. Хранение, сбои и безопасность

Полные plans/scripts/change sets/listener states хранятся в ArtifactRepository 06; большие payload могут лежать в blobs с checksum. SQL projections ускоряют поиск item IDs и diff, но source of truth — pinned ScriptRevision. Preview/оглавление — отдельный DerivedPreview с derived_from_ref; они не дописываются в immutable script после сохранения.

| Событие | Действие |
|---|---|
| Лимит ответа посреди JSON/реплики | Сохранить diagnostic, `incomplete_output`; новая попытка меньшей целой единицы, не обрезанный успешный акт |
| Crash после save до ответа tool | Idempotent повтор возвращает тот же script/change set; duplicate append запрещён |
| Dossier обновился во время письма | Старый task остаётся pinned; результат proposal, редактор делает explicit rebase/handoff |
| CAS conflict двух правок | Оба результата сохранены; модель получает diff и новое задание интеграции |
| Переставили акты | Invalidate affected ListenerState, перепроверить переходы/смысловые связи, новые reviews |
| ResearchRequest указывает на удалённый item | Исторический ref сохраняется; disposition obsolete либо explicit remapping с основанием |
| Источник отозван | Результат не допускается по старой опоре; повтор research/verification по 01/04 |
| Отмена в середине акта | Сохранённые checkpoints доступны; никакой новый ready после fenced cancel |
| Пользователь правит текст | Новая revision на тех же условиях проверки и invalidation, без обхода QA |

Источники, прошлые scripts и model outputs — данные с происхождением. Цитата «игнорируй инструкции» может обсуждаться как факт, но не меняет инструменты/права. Доступ к artifacts, retrieval и внешнему провайдеру соответствует scope/privacy 06. Нельзя сохранить private excerpt в общедоступном preview или забыть его копию в истории после purge. У автора нет tools публикации, отправки сообщений или изменения credentials.

## 12. Реализационные пакеты

Все пути ниже — целевые модули под `backend/src/podgen/writing/`, не описание существующего кода.

| Пакет | Ответственность |
|---|---|
| `domain` | StoryPlan/ScriptRevision/ScriptChangeSet/ListenerState, selectors, IDs, structural invariants |
| `planning` | Выбор маршрута истории, основание переходов, функции ведущих, обновление плана при смене досье |
| `drafting` | Прямое письмо и опытный вариант с устным черновиком, запись целого выпуска/акта/продолжения, checkpoints |
| `continuity` | Сборка spoken_view, ListenerState по непрерывному префиксу, повторный расчёт после перестановки |
| `revision` | Typed operations, diff/identity map, request remapping, global rewrite |
| `context` | Полный смысловой brief, scripts/notes, explicit previews и coverage |
| `tools` | Model-facing save/read/request/finish, runtime hooks без прямой БД модели |
| `prompts` | Versioned role templates, хорошие/плохие примеры, profile qualification |

Application use cases используют ports 06: ArtifactRepository, SourceReader, ModelGateway, TaskDispatcher. Domain не импортирует SDK/Temporal. Authoring tools используют общий admission/alias/trace dispatcher. Frontend редактора отображает spoken текст, nonspoken placeholders и provenance отдельно, показывает review текущей revision и последствия правки до запуска нового run.

## 13. Приёмка и эксперименты

| Сценарий | Обязательный результат |
|---|---|
| План обещает ответ, текст его не даёт | ListenerState не закрывает promise по плану; whole-script review находит отсутствие |
| Акт2 повторяет объяснение акта1 | Writer/reviewer видит реальный prefix; исправление проверено на полном тексте |
| Callback использует известный факт с новой функцией | Нет формального отказа за отсутствие нового claim |
| Механизм в source имеет исключение | Оно сохраняется в досье/контексте/нужном месте речи, а не исчезает в preview |
| Неизвестная причина соблазняет красивой связкой | Typed placeholder/request, нет необоснованного production финала |
| Сценарий 90 минут | Все акты/реплики сохранены, output capacity учтена, нет пропуска середины |
| Перестановка/разделение/слияние реплик | IDs/lineage и selectors однозначны; устаревшие states/reviews не reused молча |
| Исправленный факт ломает кульминацию | Повторная глобальная EditorialReview, а не только локальный фактчек |
| После review изменён один символ | Новая revision; reuse требует явной проверки соответствия, не переноса approval |
| Audio показывает неверную длительность | Содержательная правка/перемонтаж по ответственности; нет filler или fake timing |
| Retry/late result/cancel | Нет duplicate acts, lost checkpoint или несанкционированного продвижения head |
| Только ремарка объясняет причинный переход | ListenerState оставляет его открытым, первый читатель указывает слышимый стык |
| Первый save и повтор после сбоя, акт продолжается тремя записями | Один первый script без ChangeSet, далее точные пары версий, каждая реплика сохранена один раз |
| Досье изменило итог после планирования | План и финал пересмотрены на D2, P1/D2 вместе не проходят в выпуск |
| Удалён placeholder, блокирующий запрос ещё открыт | Текст и звук ждут принятого решения по запросу |
| Локальная поправка в сильной сцене | Исправлена ошибка, сохранены смысл возврата и характер ведущих. Новая версия прошла повторную проверку |

На одинаковых досье сравнить whole_episode и sequential_acts, full context и обоснованную compact view, actual-script ListenerState и отсутствие ledger. Отдельно проверить solo/dialogue, русскую и другие квалифицированные языковые пары, 15/30/60/90 минут, исторический рассказ, механизм, спорные данные и бедный корпус. Ни один профиль не объявляется лучшим только потому, что уместил больше tokens.

Контрольные эксперименты: экспертное досье изолирует авторство от research; экспертный StoryPlan изолирует planning; одинаковый script feedback с полным/неполным prefix проверяет передачу контекста. Это отдельные условия, а не преимущество одной системы в end-to-end сравнении. Независимая оценка полного текста и прослушивания — 04/05: понятность причинной цепи, полезность примеров, реальное развитие диалога, повторы, честность ограничений и качество финала. Структурная валидность остаётся необходимой технической проверкой, но не метрикой хорошей истории.
