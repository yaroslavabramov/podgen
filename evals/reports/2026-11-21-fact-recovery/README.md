# Сохранение рецензии, доприсерча и расходов

## Проверенные сценарии

1. Фактчекер дошёл до доприсерча, получил отказ по кредитам и возобновился. Рецензия сохранила доказательства из обеих попыток. Повторное открытие результата сделало ноль обращений к провайдерам. Та же проверка прошла для авторской правки. [Тест восстановления](../../../backend/tests/test_research_credit_audit_runtime.py)
2. Фактчекер повторил исходный вопрос в итоговом решении. Оба обращения получили результат одного заказа, включая случай с незакрытым вопросом. При перестановке цитат, изменении пояснения или перезапуске выпуска повторного исследования не было. Разным вопросам соответствуют разные заказы. [Тест выпуска](../../../backend/tests/test_episode_bound_research.py) · [Замеры повторного и конкурентного доступа](../2026-11-21-bound-research-orders/README.md)
3. Успешный и неудачный поиски внутри одного ответа учитываются по отдельности. Подробные замеры приведены ниже.
4. Сохранённый ответ Gemini может содержать JSON, оформление в Markdown и приложение Sources. Валидные цитаты проверяются по сохранённому тексту. Если часть цитат проверить невозможно, проверенные отрывки остаются доступны, а сам ответ остаётся незакрытым. Старый результат и его новая интерпретация хранятся раздельно. [Проверки разбора](../../../backend/tests/test_targeted_answer_parser.py) · [Переразбор сохранённых результатов](../../../backend/tests/test_targeted_partial_evidence.py)

Архивный прогон с живыми провайдерами не повторяли. Сквозные проверки использовали отдельную PostgreSQL, штатный процесс выпуска и локальные ответы провайдеров. [Замеры восстановления и доприсерча](../2026-11-21-research-recovery/README.md)

## Смешанный результат веб-поиска

В обычном выпуске на PostgreSQL локальный провайдер вернул в одном ответе успешный поиск, неудачный поиск и готовую рецензию. Контракт предыдущей версии останавливал выпуск. Новая версия приняла ответ, провела последующие этапы и завершила сборку. В обоих случаях фактчекер сделал два запроса генерации, включая первый запрос на чтение источника. Экспорт отражает один успешный поиск и один неудачный. Отдельных доказательств из результатов веб-поиска не создаётся.

| Измеренная операция | Прежний контракт и экспорт | Прежний контракт, исправленный экспорт | Новый контракт |
|---|---:|---:|---:|
| Успешные / неудачные поиски в экспорте | 0 / отсутствует | 1 / 1 | 1 / 1 |
| SQL от входа в фактчекер до остановки или возврата рецензии | 279 | 279 | 295 |
| SQL при экспорте всего запуска | 1 235 | 1 235 | 1 723 |

Числа последнего столбца относятся к выпуску, дошедшему до сборки. В первых двух запусках работа закончилась на первой фактологической рецензии, поэтому состав экспортов различается. Для исторического ответа восстановление счётчиков при экспорте обошлось без дополнительных обращений к БД или хранилищу объектов. Используется уже выгруженная квитанция провайдера. Исходные запросы и сохранённый исход проверки не переписываются. [Замеры операций, объёма данных и памяти](mixed-search-measurements.json)

Через SDK с локальным HTTP проверены также две ситуации, когда после сбоя модель должна продолжать работу. В первой веб-поиск был единственным действием, во второй одновременно понадобилось чтение документа. При отказе по кредитам возобновляется только отказавший запрос. Повторное открытие готовой рецензии не отправляет запросов провайдеру. [Проверки](../../../backend/tests/test_web_search_outcomes.py)
